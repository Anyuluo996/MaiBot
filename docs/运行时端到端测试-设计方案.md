# MaiBot 运行时端到端测试设计方案（黄金探测 + 合成对话闭环）

- 日期：2026-11-11
- 状态：草案 v1（待评审，未实施）
- 背景：2026-11-11 单日三起生产事故（tl000182fe 期限误杀 / tl00026856 误闭环+工具被裁 / 11:20 喝水提醒立项失败）全部由真实对话撞出，发现周期 2~6 小时；三起事故的直接根因（语义裁剪裁掉承重工具、期限建模缺陷、ack 误闭环）均已修复，但**检测手段仍然缺失**——现有测试无法在部署前/部署时抓住同类问题
- 已定决策：分层设计，L1（黄金 query 探测）先行；L2（test 群合成对话 E2E）其次；不注入宿主代码

---

## 1. 问题定义：测试分层的缺口

```
离线单元/胶水测试          生产真实流量
（task-loop 68 例          （发现周期 2~6h，
 toolgate 75 例，           靠用户人肉感知，
 全绿但组合盲区）           无断言无告警）
        │                        │
        └────── 缺这一层 ────────┘
     准生产自动化端到端验证
   （部署前探测 + 部署后闭环断言）
```

今天三起事故的检测面盘点：

| 事故 | 直接根因 | 离线测试为何没抓住 | 需要的检测层 |
|---|---|---|---|
| tl000182fe 期限误杀 | hint 不解析+顺延 undercut | 离线测试构造的时钟场景没覆盖「活跃时段外立项→语义到期点」组合 | E2E：真实立项→到期→闭环全链路 |
| tl00026856 误闭环 | ack 被时间窗近似判交付 | 胶水测试假设 ack 在触发前发出（生产中模型先安抚再干活） | E2E：真实 LLM 行为 |
| 喝水提醒立项失败 | toolgate 裁掉 task_submit | toolgate 测试显式传 always_keep（不测真实快照组合）；task-loop 测试不接 toolgate | **黄金 query 探测**（事前）+ E2E |

结论：缺的是「**真实组件组合 + 真实生产配置 + 可断言的合成流量**」这一层。

## 2. 目标与非目标

**目标**

1. 部署 toolgate / task-loop / 任何影响工具池的插件后，**10 分钟内**自动发现「承重工具被裁」类回归
2. task-loop 全链路（立项→期限→触发→交付闭环）有**可重复执行、可断言**的端到端验证，不依赖真实群友撞
3. 告警接 gotify（复用 watchtower 通知通道），巡检 cron 可承载，无新增常驻服务

**非目标**

- 不做宿主消息注入 API（不动主程序；合成消息走测试 QQ 账号）
- 不追求覆盖 planner 的全部模型行为（幻觉、风格漂移）——只断言「该立项的立项、该交付的交付、被裁工具可探测」
- 不新建常驻测试服务（全部脚本 + 既有 cron/gotify 承载）

## 3. L1：黄金 query 检索探测（toolgate 仓库）

### 3.1 原理

三起事故中两起的直接形态是「query 与承重工具语义距离远 → evaluate 淘汰」。evaluate 的全部输入（工具向量目录、embed 模型、语义参数、保底并集）在生产机器上都有持久化副本——**离线复算即可事前探测**，无需等真实流量。

```
黄金 query 集 ──embed──▶ query 向量 ──┐
                                      ├─▶ 复算 evaluate（与线上同参数）
semantic-vectors.npz ─────────────────┘        │
（工具向量缓存）                                ▼
                                    query → kept 名单
                                               │
                                    断言：承重工具 ∈ kept？
                                               │
                                    通过 ✓ / 失败 → gotify 告警
```

### 3.2 组件与落点

| 组件 | 落点 | 说明 |
|---|---|---|
| `bench/probe_golden.py` | toolgate 仓库 | 探测器：读 npz + config + 保底常量，对黄金集逐条复算 |
| `bench/golden_queries.json` | toolgate 仓库 | 黄金集：`{query, must_keep: [工具], note: 事故编号}` |
| `scripts/e2e_run_l1.sh` | wo4:/root/maim-bot/scripts/ | 部署后/巡检调用的包装（容器内 python -u 执行） |

### 3.3 黄金集初始清单（今天的教训即种子）

| query | must_keep | 对应事故 |
|---|---|---|
| 「岸宝1点提醒我喝水」 | task_submit | 11-11 11:20 喝水提醒 |
| 「查一下POE最新更新日志总结一下」 | web_search、web_fetch | tl00026856 |
| 「之前聊的那个事怎么样了」 | query_memory | 同上（记忆检索通道） |
| 「帮我整理这个文档发群里」 | sandbox_upload_file | 交付链路锚点 |
| 「唱歌」「用语音说」 | send_voice_message | 表达能力锚点（不保底但需 kept） |
| 「今天天气如何」（闲聊负样本） | 无断言（仅记录 kept 供漂移观察） | — |

维护规则：每起新事故追加一条；负样本定期复查 kept 漂移。

### 3.4 与线上 evaluate 的忠实度差异（诚实清单）

| 维度 | 线上 | probe 离线复算 | 影响 |
|---|---|---|---|
| 工具目录 | probe 循环预热 + 宿主实时注册 | npz 缓存快照 | 工具增删后有滞后（下次 probe 循环重建后消失） |
| 账号 gate | 按会话账号过滤 | 不过滤（全量目录） | probe 偏严（候选更多更难 kept）→ 探测失败=真失败，通过≈线上通过 |
| cache_hits 路径 | 相似 query 走缓存 | 每次全算 | 无影响（结果一致，只是慢） |
| entity 词锚 | TF-IDF 索引（生产构建） | 需复用 npz 附带的实体词索引 | 若 npz 不含则 probe 偏严，可接受 |

原则：**probe 只允许偏严不允许偏松**——偏严的通过才可信。

### 3.5 跑法与告警

- 部署后手动跑一次（部署 checklist 步骤）
- 巡检 cron（6h 既有）加一步：跑 probe，非零退出码 → gotify 推送（复用 watchtower 的 gotify token）
- 故障注入验收：临时把 `CLOSURE_CRITICAL_TOOLS` 里的 task_submit 从保底移除（本地分支），probe 必须对「喝水提醒」query 报警——**探测器自身的有效性用注入验证**

## 4. L2：test 群合成对话 E2E

### 4.1 原理

test 群（657687561，chat_prompt 即「只执行功能，不用对话」）以测试 QQ 账号注入脚本化消息，驱动**真实全链路**（MaiSaka→读空气→Planner→toolgate→工具执行→task-loop 状态机→出站），断言读三个现成数据源：

```
测试账号 ──napcat HTTP──▶ test 群消息
                             │ 真实全链路（含 LLM）
                             ▼
        ┌────────────────────┼────────────────────┐
task_loop_state.json    calls/retrieval JSONL   docker logs（出站）
（台账状态断言）          （工具kept断言）         （回应内容断言）
```

### 4.2 组件与落点

| 组件 | 落点 | 说明 |
|---|---|---|
| `scripts/e2e/scenarios.py` | MaiBot 主仓 | 场景定义：消息文本 + 断言清单 + 超时 |
| `scripts/e2e/runner.py` | MaiBot 主仓 | 执行器：napcat 发消息 → 轮询断言 → 报告 |
| `scripts/e2e/run_l2.sh` | wo4:/root/maim-bot/scripts/ | 服务器侧包装 |

前置依赖（待确认）：测试 QQ 账号挂在哪台机器的 napcat 上（ov_testing_account 记忆指向的账号），拿到其 HTTP API 地址与 test 群号。

### 4.3 场景集（v1 三条 + 一条反向）

| # | 注入消息（N 点用未来时刻） | 断言 | 覆盖 |
|---|---|---|---|
| S1 | 「岸宝明天N点提醒我喝水」（带日期） | ①台账新任务且 `due_at`≈语义到期点（±60s）②`deadline_at`≥due+l0×(1+chases) ③到点触发后 `delivered` 且出站含锚词 | 期限解析/看门狗/闭环全链（tl000182fe 回归） |
| S2 | 「帮我查一下XX然后总结发出来」 | ①台账立项 ②retrieval JSONL 该轮 kept 含 web_search ③出站非「没有联网工具」类摆烂话术 | toolgate×task-loop 组合（tl00026856 回归） |
| S3 | ack 话术探测：S1 立项后同回合「好的知道了」 | 任务不被误判 delivered（冷静窗生效） | 误闭环回归（tl00026856 第二形态） |
| S4（反向） | 「今天心情不错」 | 不立项、task_submit 零调用 | 防过度立项 |

断言容忍度：LLM 非确定性 → S1/S2 允许重试采样（同场景最多 2 次注入）；内容断言用关键词族而非全文匹配。

### 4.4 隔离与卫生

- 场景消息 goal 携带唯一 token（时间戳后 6 位），台账断言按 token 匹配任务，避免 dedupe/旧任务干扰
- 只在 test 群跑；频率默认 1 次/天（低峰 04:00）+ 手动触发；单场景 LLM 成本几万分 token，可忽略
- S1 的提醒任务到点会真出站——测试群即可，无打扰面

### 4.5 已知抓不住的

- planner 模型不用工具而凭空编造（S2 的出站断言只拦「摆烂话术」，编造但格式像样的内容拦不住——这是模型质量问题，归人设/提示词范畴）
- 深夜活跃时段门控与到期点组合（S1 用「明天」日期可覆盖大部分；跨零点顺延场景保持离线测试覆盖）

## 5. L3：canary 自主任务（可选，暂缓）

task-loop 每日自立项一个金丝雀（due=+10min，goal=「回复今天的日期」）。与 S1 链路重叠度高，**L2 落地后可省**；若 L2 因测试账号问题长期受阻，L3 作为退路（不依赖外部账号）。

## 6. 巡检集成（真实流量的事后断言，零成本层）

既有 6h 巡检追加两项只读检查：

1. **漏斗异常**：task-loop stats 的 `failed_timeout` 窗口增量 >0 且 `trigger_errors` 连续 → gotify
2. **真实流量 kept 抽查**：当日 retrieval JSONL 中含「提醒/查证/整理」意图词的轮次，断言对应承重工具 ∈ kept（事后版 L1，抓 probe 覆盖外的真实 query 形态）

## 7. 实施阶段（可独立合入回滚）

| 阶段 | 内容 | 仓库 | 工作量 | 验收 |
|---|---|---|---|---|
| 一 | L1 探测器 + 黄金集 + cron/gotify 接线 | toolgate | 半天 | 黄金集全过；故障注入（移除保底）必报警 |

回滚：全部为新增脚本/配置，git revert + 删 cron 步骤即回滚；不触碰插件运行时行为。

## 8. 与既有资产的关系

- `eval_retrieval.py` / `shadow_rate=0.1`（toolgate 既有）：反事实 HitRate 对账 = **事后、统计层**；本方案 L1 = **事前、确定性断言**。互补不重复；L1 落地后再评估 shadow_rate 是否还需维持（+20k token/轮的影子采样可考虑降频）
- `scripts/check_blocking_hook_kwargs.py`（主仓既有）：静态契约层，与本方案正交
- 6h 巡检 cron（既有）：L1/第 6 节检查项的承载方，不新建调度
