# 自主任务链路审计方案（anyul.task-loop × anyul.mcp-toolgate）

- 日期：2026-11-11
- 状态：草案 v1（待评审，未执行）
- 背景：2026-11-11 单日三起生产事故（tl000182fe 期限误杀 / tl00026856 误闭环+工具被裁 / 11:20 喝水提醒立项失败）当日全部修复部署（task-loop v0.2.1、toolgate v0.9.4）。热修在时间压力下完成，且事故家族的根因（闲聊 query 与承重工具语义距离远 → 语义裁剪漏保底）是「靠事故驱动补漏」的模式——需要一次系统审计回答：**热修本身是否引入新问题、存量代码还有多少同类缺陷、生产历史数据里还有多少未被发现的受害轮次**。
- 定位：与《运行时端到端测试-设计方案》（v1 待评审）互补——E2E 方案管**事前检测**（部署后 10 分钟内发现回归），本方案管**存量清查与缺陷扫描**（热修质量、代码横向、历史数据回溯）。审计产出直接回填 E2E 黄金集与离线回归用例。

## 2. 目标与非目标

**目标**

1. 热修质量：v0.2.0→v0.2.1、v0.9.1→v0.9.4 两轮改动面逐点复审，确认未引入新缺陷（尤其冷静窗与追讨/闭环的交互、保底集单一事实源的三处派生一致性）
2. 横向扫描：在两个插件内找出与事故家族同类的潜伏缺陷（静默失败、状态机边界、时间窗口叠加、并发写状态）
3. 数据回溯：用 retrieval/calls JSONL + prompt 记录对账，产出**历史受害轮清单**（被裁承重工具的轮次、误闭环任务、未立项请求），量化事故家族的真实规模
4. 部署态对账：本地仓库 vs wo4 运行态的一致性（版本、config 快照分叉、启动护栏日志、备份卫生）
5. 裁决悬案：为 top_k 15→18 暂缓判据提供第一份实证（dropped_rank/dropped_top3 反事实数据）

**非目标**

- 不改运行时行为——审计全程只读；发现的缺陷按分级另开修复任务（P0 除外，见 §6）
- 不重复 E2E 方案的建设（互补不重叠）
- 不审计宿主代码

## 4. 审计轨道（按执行顺序）

### 轨道 1：部署态对账（先跑，定审计基线，~1h）

本地（D:\app\MaiBot\plugins\）与 wo4 运行态逐项对账：

1. **版本与 commit**：两插件 manifest 版本 vs wo4 实际加载版本；本地 git HEAD vs 部署 commit（62e9d6b / 07a90b4+d4c96d5 / f08a1c2 / 975052b）——防「本地已修、线上旧版」或反向分叉
2. **config 快照全键 diff**（K7）：wo4 两插件生产 config.toml 逐键 vs 代码默认值——不止 always_keep，top_k / threshold / entity 参数 / shadow_rate / mcp_min_keep / task-loop 全部键都可能存在同样的「快照固化」分叉；产出分叉键清单及「代码默认值已演进但线上仍旧值」的标记
3. **启动护栏三验证**：容器启动日志确认 `always_keep=11`、rank 席 <4 WARNING 零触发、零 Traceback
4. **备份卫生**：/root/maim-bot/plugin-backups/ 完整性；plugins/ 内无备份目录（ID 重复全阻止加载坑）；`plugins/task-loop-0.2.0.tar.gz` 旧打包残留处置；`_patch_wo4.py` 重跑风险标注（会盖回旧快照）

### 轨道 3：生产数据回溯（半天，与轨道 2 可并行）

对账三数据源，产出**受害轮清单**。步骤 0 先确认数据窗口：`stats_store._cleanup_expired` 的保留期、wo4 data_dir 实际现存几个日期的 JSONL——回溯深度以数据窗口为上限（待拍板 §8.1）。

**对账 1：意图词族 × kept（找被裁轮次）**

```
retrieval-*.jsonl 逐行：
  query 含意图词族（提醒|查|搜索|整理|总结|文档|语音|发群…）
  且 kept 不含对应承重工具（web_search/web_fetch/query_memory/task_submit/sandbox_upload_file/send_voice_message）
  → 候选受害轮
  → 用同 ts 的 calls 行验证后续行为（摆烂/零工具调用/tool_search 落空）
  → 用 prompt 记录（/MaiMBot/logs/maisaka_prompt/planner/<session>/<ts>.json 的 tool_definitions）实证工具池
```

产出列：ts / session / query / 被裁工具 / 后果分类（摆烂|零回应|误闭环|无影响）。同时统计 dropped_rank 里 cos≥threshold 的挤出事件（K5 判据①）——**此对账直接裁决 top_k 15→18 是否启用**。

**对账 2：task_loop.log + task_loop_state.json 终态复盘**

- failed（fail_overdue）/abandoned（TTL）任务全列：归因分类（工具被裁|期限缺陷|模型摆烂|正常失败）
- delivered 任务 goal 与出站锚词对照：**误闭环存量检出**（prompt 记录还在的查交付内容，不在的标注数据已滚动）
- 立项漏斗：task_submit 调用数 vs 群内提醒类请求数（11:20 喝水样本 K8 作为已确认锚点核对方法有效性）

**对账脚本纪律**：先在本地 eval_data/ 样本（retrieval/calls-20261104/05.jsonl）验证脚本，再上 wo4 生产数据；一次性脚本放 /tmp，有复用价值的（意图词×kept 对账）沉淀到 wo4:/root/maim-bot/scripts/ 供 6h 巡检复用（衔接 E2E 方案 §6 第 2 项）。

### 轨道 4：代码横向扫描（1 天，两插件全量）

与事故家族同类的潜伏缺陷，按模块过：

**task_ledger.py**

- 门控链（create_task:298）：`find_duplicate`(268) 的相似度判定——每日重复提醒类请求是否被误杀 dedupe（行为是否符合设计意图、有无测试覆盖）；会话并发(332)/日限的边界值（恰好等于限额时）
- `_tl_tick` 四阶段顺序（due→chase→fail→expire）的状态竞争：同一拍内任务被连续推进两态的可能；tick 与 after_send hook 并发修改 ACTIVE 任务的锁面
- stop_task / stop_all / resume_for_restart 的状态迁移完备性（不存在能到达但无出路的中间态）

**time_hint.py + delivery.py**

- `_resolve_clock`(75) / `_cn_number`(57) 的中文数字与时钟归一边界（半、刻、两）；跨零点窗口（tests 已用收窗规避，说明有已知坑——正式盘点 `next_window_open`(60) 的跨零点正确性）
- 软期限/硬期限/无期限三态在 tick 四阶段中的完整矩阵推演（每种组合的到期行为应有唯一确定值）

**semantic_gate.py**

- `filter_tools`(728-1041) 全流程分支：lex 全落空模式下 kept_always 是否仍在最前保（保底并集在 fallback 分支不失效的证明）；MMR 池与 entity 席、unscored 全保的席位数算术复核（K4 的 remaining≤0 触发可能性在此量化）
- 工具向量缓存增量补块：失败工具进 unscored 必保——embed 持续失败时「全量 unscored」的退化形态对 hook 超时的影响
- `extract_query`(150) 对闲聊 query 的提取质量（三起事故的 query 形态回放）

**三子闸门叠加**（account_gate / identity_gate / reminder_gate × 语义裁剪）

- 三个 BLOCKING/OBSERVE 钩子叠加顺序与失败组合：账号被 gate 的会话，语义裁剪输入是什么（空池？全池？）
- `scripts/check_blocking_hook_kwargs.py plugins` 全量跑，0 ERROR 过（toolgate 2 个 BLOCKING hook）

**工具描述关键词贫瘠扫描**（K6）

- 对全部注册工具 description 做覆盖扫描：字数下限、动词/宾语词族、与黄金集 query 的词面距离；产出「描述贫瘠工具清单」——这是比 always_keep 补漏更上游的治理项

## 5. 取证纪律与证据标准

- **全程只读**：与巡检同一约束——除只读查询外禁止修复、重启、改配置；P0 发现也先记录，处置走 §6 流程
- 远程命令一律加 timeout；SSH 用主机别名 wo4；`docker logs --since` 一律绝对 RFC3339（+08:00）时间戳（相对时长偏差坑）
- 每个发现必须带 `file:line` 或 JSONL 行号/日志时间戳证据；结论零「可能/大概」——不区分「已证实」与「高度怀疑」的发现不进报告正文（端到端取证排误的既有教训：探针证据来源、匹配范围、提前退出逻辑先自审，防日志截断与出站文本误匹配造成假发现）
- 探针脚本先在 eval_data 样本上验证再上生产数据
