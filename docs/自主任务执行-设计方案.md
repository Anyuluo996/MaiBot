# MaiBot 自主任务执行设计方案（对话驱动 · 执行到结果）

- 日期：2026-11-07
- 状态：草案 v1（已定方向，未实施）
- 已定决策：**纯插件实现**（不改主程序）；v1 执行后端 = **planner 自主通路 + pi_agent 沙盒** 双路
- 拟定插件名：`anyul_task_loop`（候选：`anyul.task-exec`）

---

## 1. 目标与定位

让 bot 从对话内容中**自发识别**值得做的事，立项后台执行，**一直做到拿到结果**，再以自然的口吻回到原会话交付：

```
群友："这游戏新版本的兑换码有人整理吗"
  → 捕捉：规划器判定值得立项（或插件兜底扫描命中）
  → 立项：台账建任务（目标+验收标准+预算），bot 可先回一句"我去查"
  → 执行：后台多步工作（检索/生成/跑代码），跨消息、跨重启存活
  → 验收：三层闸，不过关打回重做
  → 投递：proactive 唤醒规划器，自然接话交付结果
```

定位边界：

| 概念 | 归属 |
|---|---|
| bot 欠的**答**（该回没回） | `anyul_open_loop`（欠答守护），维持现状 |
| bot/群友欠的**事**（该做没做、要做要做完） | 本插件（欠事守护） |
| 编码任务的**专精通道**（/pi 命令、定向派活） | `maimai_pi_agent`，维持不动；本插件把它的沙盒后端当执行器复用 |

一句话：**open-loop 管"嘴债"，task_loop 管"手债"。**

## 2. 参考项目与可借鉴模式

### 2.1 OpenClaw（原 Clawdbot）—— 自主循环三件套

- **cron 定时任务 + heartbeat 心跳注入**（默认 30min，把 HEARTBEAT.md/scratch 注入上下文，agent 自查有无值得行动的事）
- **`NO_REPLY` 静默纪律**：巡检无实质进展时静默返回、不打扰用户；结果经 delivery 策略投递
- **activeHours / idleOnly**：限制执行时段、前台优先；**scratch 是任务私有上下文**（存任务自身的检查单，修订带版本防冲突）
- **subagent**：长任务派给隔离子代理，结论回主会话，保持主上下文干净
- 教训（心跳迁移文档自述）：周期监控要收敛为**普通可编辑的任务**（schedule/prompt/delivery/run history 一体），而不是散落的全局特殊配置

### 2.2 Cindy（makecindy/cindy，Apache-2.0）—— 工作区与执行引擎分离

- 核心原则：**agent workspace ≠ agent execution engine**。任务中途可换 harness/模型，工作现场（文件、状态）不丢，切换时"交接或重建引擎上下文"而非强求内部状态一致
- **立项即验收标准**（shared goal + clear acceptance criteria）：规划/并行执行/独立评审三种 agent 分工，靠事先写明的验收标准对齐
- automations（周期例程）+ 聊天渠道（Slack/Telegram）投递 + Skills/MCP 扩展

### 2.3 Alma + herdr（yetone）—— 注意力路由与执行/呈现分离

- herdr 是承载 Claude Code/Codex/pi 的运行时，Alma 是呈现层：**执行基底与对话呈现天然两层**
- **"Needs you first"**：agent 等待回答或权限时浮到最前，问题以**按钮/选项**形式送达，人只在该出场时被打扰
- agent 停止/等待才推送——**由事件驱动注意力，而不是轮询轰炸**

### 2.4 自有资产

| 资产 | 可复用 | 位置 |
|---|---|---|
| pi_agent 派活意图链 | 关键词粗筛 + 内联 LLM 判定（`{"kind","sure","title"}`，sure≥0.8）+ before_request 注入提示、决定权留规划器 | `plugins/maimai_pi_agent/intent.py:82-147` |
| pi_agent 三层验收闸 | ①占位符/敷衍扫描 ②产物存在性 ③LLM 评审 `{"passed","reason"}` | `plugins/maimai_pi_agent/review.py:27-132` |
| pi_agent 打回重做 | 同工作区重跑（原任务+上轮产出+验收意见），`run.attempt<N>.jsonl` 归档 | `review.py:135-160`、`pi_client.py:207` |
| pi_client 提交-轮询 | 绕开 60s 工具 RPC 超时的 REST 模式 | `plugins/maimai_pi_agent/pi_client.py` |

### 3.2 边界（设计必须绕开的）

| 边界 | 事实 | 对策 |
|---|---|---|
| 工具/Hook RPC 60s 超时 | 组件调用默认 60s，超时即断 | 执行一律**提交-轮询**：`task_submit` 秒回 task_id，工作在插件后台 asyncio 任务里做 |
| 无宿主 cron | 插件没有调度能力 | 插件自起心跳循环（pixiv 先例） |
| 只有 KV 存储 | 不能直连宿主业务库 | 台账落 KV，自管索引与清理 |

| 频率=0 会话吞主动回合 | proactive 触发在静默会话被 `_handle_silent_turn` 吞掉 | 投递降级 `send.text`（见 5.5） |
| modified_kwargs 整体替换 | BLOCKING 钩子返回必须 `{..., **kwargs}` + 具名参数显式回填 | 遵守 AGENTS.md 规范 + 过 `scripts/check_blocking_hook_kwargs.py` |
| 旧 EventHandler 死路径 | `ON_MESSAGE` 等事件在新运行时不触发 | 只用命名 Hook 与能力 |
| KV/DB 不可跨重启丢在途 | open-loop 实锤教训 | 台账持久化 + on_load 恢复（见 5.6） |

## 4. 总体架构

```
                    ┌──────────────────────────────────────────────────┐
                    │              anyul_task_loop 插件                 │
 对话消息            │                                                  │
    │               │  捕捉双路            任务台账(KV 状态机)           │
    ├─ A 规划器自主 ─┼─► @Tool task_submit ─► candidate → open ──┐      │
    │   （主路）      │                        （goal+验收+预算）  │      │
    ├─ B after_process 兜底扫描 (OBSERVE)                        │      │
    │   （候选线索，决定权仍在规划器）                              ▼      │
    │               │                                        执行层     │
    │               │   心跳调度器(60s tick) ── due/poll/chase/deliver │
    │               │        │                       ┌────────────────┤
    │               │        │                       │ L0 planner 自主 │
    │               │        │                       │ L1 pi_agent 沙盒│
    │               │        │                       │ L2 自建循环(预留)│
    │               │        │                       └───────┬────────┘
    │               │        │                          泛化三层验收+打回
    │               │        │                               │
    └─ send_service.after_send (OBSERVE) ◄── L0 闭环检测       ▼
                    │        │                          投递器
                    │        │                    proactive.trigger 首选
                    │        │                    └降级 send.text
                    │        └─ needs-you 结构化追问（Alma 模式）
                    └──────────────────────────────────────────────────┘
```

任务状态机：

```
candidate → open → running → verifying → delivering → delivered
                        │            │
                        │            └─(验收不过,轮次未尽)→ running(打回重做)
                        │            └─(轮次尽/预算尽)──→ failed
                        ├─(缺信息/需确认)→ stalled(needs-you) ─(补答)→ running
                        │                     └─(waiting TTL 过期)→ abandoned
                        └─(手动/超软期限)──────────────────────→ abandoned
```

## 5. 关键机制设计

### 5.1 捕捉：双路

**路 A · 规划器自主判定（主路）**

插件注册 `@Tool("task_submit")`，规划器带着完整对话上下文自己判断"这件事值得开后台任务"：

```
参数：goal(必填，要做成什么)、title(短标题)、backend(留空=自动选择: "planner"|"pi")、
      acceptance(验收标准：怎样算做完)、deadline_hint(软期限，如 "今晚"/"2h")
行为：校验门控 → 建台账 → 立即返回 task_id（秒回，不阻塞）
描述门槛（写进 detailed_description）：只用于"当下聊不完、需要多步/多轮/等结果的事"，
      例：要查证/整理的资料、要生成的代码或文件、说好晚点给的东西；
      不用于：一句话能答的问题、闲聊、提醒自己关注（用 wait）
可见性：默认 visible 直进工具池（deferred 池需 planner 先 tool_search 发现，flash 级模型
      下一轮容易只输出文本计划——pi_agent 生产经验），配置项可调 deferred
```

这是"自发"的最高质量来源——规划器见到的上下文比任何前置过滤器都全，且**执行决定权天然在规划器**（与 pi_agent 哲学一致）。

**路 B · 插件兜底扫描（防漏，P2）**

`chat.receive.after_process` **OBSERVE** 模式（不改消息、后台并发、零延迟影响）：
关键词粗筛 → 异步 `ctx.llm.generate` 判定（沿用 `intent.py` 模式，预算 2.5s，输出 `{"kind","sure","title","acceptance"}`）→ 命中不直接执行，只登记 candidate 并在该会话**下一次** planner 回合经 `maisaka.planner.before_request` 注入一行线索提示（"[task_loop] 检测到任务线索：…，可评估是否 task_submit"）。防刷对齐 pi_agent：同 message_id 不重判、每会话日限、TTL。

例外：**跟进守护类**（"晚点告诉我X""明天提醒我关注Y"）不需要执行器，兜底路可直接立项，只等投递节拍。

### 5.2 立项与台账

任务 = KV 单键 `task:{id}`，另维护 `session:{stream_id}:open` 索引键与全局日计数键：

```
task_id:    tl_{seq}_{rand}
核心字段:    title / goal / acceptance / backend / origin(平台,chat_id,msg_id,发起人)
            / stream_id / state / created_at / deadline_hint
预算字段:    max_rounds(默认2) / max_duration_min(L0=10, L1=30) / llm_call_cap(默认12)
花费字段:    rounds / llm_calls / attempts[](每次含 backend、起止、结果摘要、评审结论)
投递字段:    last_deliver_at / deliver_attempts / stall{question, asked_at}
```

- **去重**：同会话 open 态任务做标题/目标相似粗判（编辑距离+关键词），命中则合并并 bump
- **门控**：每会话并发 open ≤2、日立项 ≤20；全局并发 ≤3、日全局 ≤60；超限拒绝并回执原因
- **立项即验收**（Cindy 模式）：acceptance 缺省时用 goal 兜底，但工具描述鼓励规划器写明——后续 LLM 评审以它为准绳，避免自由心证
- **归档**：delivered/failed 保留 14 天后清理，控制 KV 体积

### 5.3 执行层：工作区与执行引擎分离（Cindy 模式）

台账、验收标准、attempt 历史归**插件**；执行器是无状态适配器，可换、可重试、可降级：

```python
class Backend(Protocol):
    async def submit(self, task) -> Handle        # 提交即返回
    async def poll(self, handle) -> PollResult    # 状态/产出
    async def cancel(self, handle) -> None
```

**L0 · planner 自主通路（backend=planner）** —— 复用主程序现成的 16 轮循环+全部工具（web_search、fetch、记忆检索、MCP…），零新增执行设施：

1. 心跳 due 节拍 → `maisaka.proactive.trigger` 注入**任务卡**（goal + acceptance + 原对话锚点摘要 + 软期限），规划器多轮完成并自然 reply——**执行与交付一次完成**
2. **闭环检测**：`send_service.after_send`（OBSERVE）观测到本会话 bot 出消息且存在 running 的 L0 任务（TTL 窗口内）→ 标记 delivered。v1 用时间窗近似不做相关性判定，配套约束：**每会话同时只允许 1 个 L0 在途**，消除歧义
3. **追讨**：超 max_duration 未闭环 → 心跳 chase 节拍再 trigger 一次（标注"上一任务尚未完成"）→ 仍超时 → 转失败或降级 L1（可配）

**L1 · pi_agent 沙盒通路（backend=pi）** —— 复用已部署的 aio-sandbox + pi：

1. 心跳轮询器直接 REST 提交（自带精简 pi_client，不对 pi_agent 插件做进程内依赖），提交即返回
2. 后台轮询直到完成，拉取产物摘要
3. 过泛化三层验收；不过且轮次未尽 → 同工作区重跑（打回，见 5.4）
4. 沙盒每日 05:13 重置的遗留风险：poll 发现异常中断 → 自动重新提交续跑（`--session` 续接语义未验证，列入遗留）

**L2 · 插件内自建 LLM 循环（预留，不在 v1）**：`ctx.llm.generate` + 跨插件 API（如 anyul_web_search）做多步检索循环，独立性最强，等 L0/L1 数据说明确有缺口再立项。

### 5.4 验收与打回（pi_agent 三层闸泛化）

| 闸 | 适用 | 逻辑 |
|---|---|---|
| ① 完整性质检 | 全部 | 占位符/敷衍模式正则（"待补充/此处省略/篇幅所限"…），`review.py:27-43` 泛化 |
| ② 产物存在性 | L1 | 声称已产出文件但工作区为空，`review.py:48-55` 泛化 |
| ③ LLM 评审 | 全部 | `ctx.llm.generate(task_name="utils")`，输入 goal+acceptance+结果，输出 `{"passed","reason"}`；评审失败=inconclusive 不阻塞交付（`review.py:77-132` 泛化） |

- 打回：不合格且 rounds 未尽 → 同工作区重跑，prompt = 原任务 + 上轮产出（截断）+ 验收意见；轮次尽 → 带 `⚠️ 验收未通过：<reason>` 前缀交付，不掩盖
- L0 不做二次评审：规划器已把结果作为回复说出，交付即闭环；台账仅记录自评

### 5.5 投递：注意力路由（Alma/OpenClaw 模式）

按优先级四类投递，全部过**每会话投递冷却（默认 10min）+ active_hours（默认 08:00–23:00，窗口外只投 needs-you 与失败终态，其余攒到窗口开投）**：

| 类型 | 通路 | 说明 |
|---|---|---|
| 任务完成 | `maisaka.proactive.trigger` 注入完成卡（结果摘要+原对话锚点），规划器自然汇报，可引用、可补充 | 首选；保持"bot 自己想、自己说" |
| 完成降级 | trigger 后 N 分钟（默认 5）`after_send` 仍无观测 → `ctx.send.text` 直发结构化结果卡 | 兜静默会话（频率=0 被吞）与规划器不作为 |
| needs-you 追问 | 任务 stalled（缺信息/需确认）→ 投**结构化追问**（Alma 模式：编号选项，"回复 1/2 或直接补充"），带 waiting TTL（默认 2h），过期自动 abandoned(原因=需补充信息) | 事件驱动，人只在该出场时被打扰 |
| 静默 | 心跳巡检、无实质进展的中间状态一律不投 | OpenClaw `NO_REPLY` 纪律 |

预算耗尽/验收终败的 failed 任务向**发起会话**投一次失败说明（含已花费轮次），可选抄送管理员会话。

### 5.6 心跳调度器

`on_load` 起单一 asyncio 循环（60s tick），`on_unload` cancel + 状态落盘（pixiv 先例）：

| 节拍 | 职责 |
|---|---|
| due | 到点的 open 任务启动执行（L0 trigger / L1 submit）；跟进守护类到点直接进 delivering |
| poll | L1 在途轮询、产物拉取、异常中断重提 |
| chase | L0 超时追讨、needs-you TTL 过期结算、软期限到期提醒 |
| deliver | active_hours 内放行排队中的投递 |

**跨重启恢复（open-loop 教训）**：on_load 扫 KV——L0 running 任务重新排队 due；L1 在途从 attempts 恢复轮询句柄续 poll；needs-you 保持等待；不可恢复的标 failed(原因=进程重启)。台账每次状态迁移即写 KV（写放大可接受，任务量级小）。

### 5.7 防失控与安全

- **预算**：任务级（轮次/时长/llm_call_cap）+ 会话级（并发/日限）+ 全局级（并发/日限）三层帽；超限拒绝并在管理员会话日结告警
- **注入面**：goal 源自群聊=不可信文本——台账存原文，注入提示词时定界包裹为数据块（`<task_source_message>…</task_source_message>`）；L0 通路天然在 prompt-guard 现有防线内；L1 通路沙盒隔离、无宿主密钥（pi-agent 报告结论）
- **kill 面板**：`/tl_list`（在途台账）、`/tl_stop <id|all>`、`/tl_pause`（全局暂停捕捉与调度），Command 元数据 permission=operator
- **事件循环纪律**：全异步；判定 LLM 2.5s 预算内联（pi_agent 先例）；无同步 IO、无线程
- **BLOCKING 钩子契约**：before_request 处理器返回 `{..., **kwargs}` + items/session_id 显式回填，提交前过 `scripts/check_blocking_hook_kwargs.py`

## 6. 与现有插件的边界与协同

## 8. 分期落地

| 期 | 内容 | 验收标准 |
|---|---|---|
| **P0 最小闭环** | 台账+心跳+`task_submit`+L0 planner 自主通路+after_send 闭环+投递降级+`/tl_*` 命令 | 群里说"帮我查X整理给我"→bot 立项→后台做完→自然接话交付；容器重启后任务不丢 |

## 9. 风险与遗留

| 风险 | 缓解 |
|---|---|
| 规划器滥立项（小事也 task_submit） | 工具描述明确门槛 + 三层门控 + `/tl_list` 可见 + P0 观察期后调 |
| proactive 被静默吞（频率=0 会话） | after_send 观测降级 send.text（5.5） |
| L0 闭环误判（时间窗近似） | 每会话 L0 并发 1；P2 可加轻量相关性判定 |
| pi 沙盒 05:13 重置杀长任务 | poll 异常中断自动重提；`--session` 续接语义未验证（pi-agent 报告遗留，一并跟踪） |
| 成本失控 | llm_call_cap + 全局日限 + 管理员日结告警 |
| KV 体积 | 14 天归档清理 + 任务量级天然小 |
| 共享 Runner 循环饿死 | 全异步纪律，评审/判定全部走 ctx.llm.generate 与 aiohttp |
| 判定与 planner 抢同一模型池 | 判定输出上限收紧；若挤兑，判定切 fast_model（配置项） |

## 10. 设计取舍记录

- **为什么不直接用内置 subagent**：它是规划器自愿调用的实验性工具，插件无编程式入口；但它的"后台任务+结论回投+主动唤醒"骨架验证了本设计的通路可行性。远期若宿主将其泛化为插件能力，L0 可平滑迁移。
- **为什么投递首选 proactive.trigger 而非直接 send.text**：保持 bot"自己想、自己说"的人设一致性（可引用原对话、组织语气）；send.text 仅作降级，避免工具腔。
- **为什么 L1 不进程内依赖 pi_agent 插件**：pi_agent 已部署稳定（wo4 v0.3.0），不动它；自带精简 pi_client + 泛化验收，代价是少量逻辑复制，二期 API 化收敛。
- **为什么兜底扫描放 P2**：先验证主路（规划器自主判定）的触发率，避免一上来就在每条消息上加 LLM 判定成本。
