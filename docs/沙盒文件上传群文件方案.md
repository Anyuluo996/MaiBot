# 沙盒文件上传群文件方案

- 日期：2026-10-02
- 状态：v1.5.0 已实现并部署 wo4（2026-10-02）：容器端口发布、跨机拉取、setsid 存活、[h] 清理模式均真机验证通过；待群内端到端验收
- 范围：maimai_sandbox 插件 v1.5.0（新增 `sandbox_upload_file`）；群管插件侧无新改动（v2.16.0 已就绪）

## 1. 背景与目标

Bot 在 aio-sandbox 容器内执行下载、导出、打包任务后，产生的文件停留在沙盒容器文件系统中。目标是一条指令把沙盒内任意文件传入 QQ 群文件，要求：

- 小文件、大文件全覆盖。
- 不依赖三容器文件系统互通。
- 同机部署（wo4）立即可用；跨机器部署预留扩展点。

## 2. 已完成部分（群管插件 v2.16.0，2026-10-02）

群管插件已提供 `/upload <文件URI> [文件名]` 命令，经 `adapter.napcat.action.call` 透传 NapCat `upload_group_file`，以 retcode==0 判定成功。要点：

- 文件 URI 支持 `http(s)://`、`base64://`、`file://`；裸本地路径直接拒绝。
- 文件名缺省从 URI 末段推断（剥 query/fragment，URL 解码中文）。
- 权限：群主/群管理员/全局管理员；成功记入操作日志（action=upload_file）。
- napcat_tools action 目录收录 `upload_group_file`，默认不进白名单。
- 回归测试 12 项，插件全量 252 项通过。

本方案不改动群管插件。沙盒插件复用同一 NapCat action，两条入口并存。

## 3. 架构约束（已验证事实）

实施前需要知道的约束，全部来自已有验证或生产实测：

| # | 约束 | 影响 |
|---|------|------|
| 1 | 三个容器文件系统隔离：maim-bot-core（插件进程）、aio-sandbox（文件所在）、napcat 适配器（`file://` 解析处） | 沙盒路径不能直接作为 `file://` 传给 napcat |
| 2 | `base64://` 载荷走 MaiBot↔适配器↔napcat 的 WS 控制链路；大文件实测导致 WS 断开，且 base64 有 1.33 倍体积放大 | base64 只适合小文件，需要大小阈值 |
| 3 | OneBot/NapCat 没有分片上传群文件的 API | 分块传输不可行，不作为备选 |
| 4 | `http://` URI 由 napcat 进程主动 GET；唯一判据是该 URL 从 napcat 网络位置可达，不需要公网 | 大文件数据面：让 napcat 直连沙盒容器拉取 |
| 5 | AIO Sandbox `/v1/file/read` 只支持 utf-8 文本 | 二进制文件经沙盒内 shell `base64 -w0` 取回 |
| 6 | maimai_sandbox manifest capabilities 仅有 `send.text` / `send.image` | 调 napcat 前必须在 manifest 增加 `api.call` |
| 7 | wo4 双 bot 各挂一套 napcat 适配器，同名 `adapter.napcat.*` API 会报「API 名称不唯一」（群管已用 `identity.adapter_api_prefix` 解决） | 沙盒插件需要同款前缀配置 |
| 8 | 实际拓扑：MaiBot + aio-sandbox 在沙盒宿主（easytier IP 10.126.126.2），NapCat 在 wo4（10.126.126.3），两机经 easytier 内网互通 | 大文件走 `http://10.126.126.2:18630`，需沙盒容器把 18630 发布到宿主（见第 6 节步骤 1） |

## 4. 方案设计

### 4.1 总体思路：控制面与数据面分离

WS 控制链路只传指令（action 调用、几十字节）；文件数据按大小自动选路：

```
sandbox_upload_file(path, [name])
        │
        ├─ 文件 ≤ base64 阈值（默认 15MB，可配）
        │      控制面直传：沙盒 shell base64 -w0 → base64:// → upload_group_file
        │
        └─ 文件 > 阈值
               数据面直连：沙盒内临时 HTTP 服务 → upload_group_file(http://10.126.126.2:18630/...)
               napcat 经 easytier 内网直连沙盒宿主拉取文件字节
```

### 4.2 `sandbox_upload_file` Tool 编排流程

输入参数：

- `path`（string，必填）：沙盒内文件绝对路径，通常以 `/home/gem/` 开头。
- `name`（string，可选）：上传后的文件名，缺省取 path 末段。

执行步骤（两条路径共用的前置）：

1. 解析发起者与群号。发起者识别复用 `_sb_sender_id`；群号从 Tool kwargs 的 `message.message_info.group_info.group_id` 解析（与 `_sb_sender_id` 解析 `user_info` 同一结构层次）。群号缺失时返回「仅支持在群聊中上传群文件」，不降级为私聊发送。
2. 校验权限：仅 `security.allowed_users`（管理员）可发起。上传属于把沙盒内容外发到群，比沙盒内执行更严格，不进 tiered 分层放行，识别不到发起者按 fail-closed 拒绝（与沙盒插件现有高危操作门一致）。
3. 查文件：`shell_exec` 执行 `stat -c '%s' <path>` 取字节数。文件不存在时把 shell 错误原文返回给模型。

小文件路径（≤ `upload.max_base64_mb`）：

1. `shell_exec` 执行 `base64 -w0 <path>`，从 stdout 取 base64 文本。
2. 调用 `ctx.api.call(api_name=<带前缀的 adapter.napcat.action.call>, action_name="upload_group_file", params={"group_id": 群号, "file": "base64://<内容>", "name": 文件名})`。
3. 校验 retcode==0，成功返回文案，失败返回 NapCat message 原文。

大文件路径（> `upload.max_base64_mb`）：

1. 在沙盒内启动临时 HTTP 服务（后台、脱离会话）：

   ```
   setsid nohup python3 -m http.server 18630 --directory <path 的父目录> >/dev/null 2>&1 &
   ```

   `setsid` 脱离进程组，防止 `shell_exec` 的 hard_timeout 到期时连带终止服务进程（此行为需在部署验证中确认，见 7.2）。
2. 探测就绪：`shell_exec` 执行 python3 单行（urllib）请求 `http://127.0.0.1:18630/<quote(文件名)>`（curl 未必在镜像里，python3 必在），失败重试至多 3 次、每次间隔 1 秒。仍失败则清理进程并报错（文案含端口号与 pkill 清理命令）。
3. 调用 `upload_group_file`，`file` 参数为 `http://<upload.sandbox_host>:<upload.http_port>/<quote(文件名)>`（文件名按 RFC 3986 percent-encode，处理中文与空格）；部署值为 `http://10.126.126.2:18630/...`。
4. 无论上传成败，在 finally 中清理服务：`pkill -f 'http.server 18630'`。清理失败记 warning 日志（残留进程只占用容器内一个端口；端口被占时下次探测失败会报错提示）。

两条路径成功后都要求：沙盒内不残留 `http.server` 进程（小文件路径不涉及）。

### 4.3 端口管理

- 固定端口 `upload.http_port`（默认 18630，避开 wo4 公网开放段 18080-18130），不起端口池。
- 端口被残留进程占用时表现为服务起不来、文件探测失败，报错文案带端口号与 pkill 清理命令。固定端口让残留可见、可排查，比自动漂移更可控。

### 4.4 配置项（`[upload]` 分区，新增）

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `enabled` | bool | `false` | 总开关；关闭时 Tool 返回未启用 |
| `max_base64_mb` | int | `15` | 超过该大小走 HTTP 数据面 |
| `http_port` | int | `18630` | 沙盒内临时 HTTP 服务端口（避开 18080-18130） |
| `sandbox_host` | string | `10.126.126.2` | 拼进 napcat 拉取 URL 的主机地址（沙盒宿主的 easytier 内网 IP；napcat 所在 wo4 为 10.126.126.3，内网互通） |
| `adapter_api_prefix` | string | 空 | 多适配器实例 API 前缀，语义与群管 `identity.adapter_api_prefix` 相同；为空时直接用 `adapter.napcat.action.call` |

manifest：capabilities 增加 `api.call`；版本升至 1.5.0。不设 timeout_seconds 配置——base64 取回固定 60 秒、napcat 等待由宿主控制，插件层无消费点，不做假配置。

### 4.5 跨机器部署的预留（本期不实现）

本部署本身就是跨机器场景（沙盒宿主 10.126.126.2、NapCat 所在 wo4 10.126.126.3），easytier 内网直连即上述 HTTP 数据面路径，无需额外改动。若未来出现内网完全不通的部署（如 NapCat 在无内网互通的机器上），扩展路径为 R2 中转：沙盒上传、不可猜测 key + 短 TTL、NapCat 拉公网 URL；涉及新凭据与清理策略，作为后续版本单独实现，本期不做。

## 6. 部署步骤（沙盒宿主 10.126.126.2 + wo4/NapCat 10.126.126.3）

1. 发布容器端口：沙盒所在机器的 aio-sandbox 容器把 18630 发布到宿主机——compose 的 ports 增加 `"18630:18630"`（或绑定 easytier 接口 `"10.126.126.2:18630:18630"` 更收敛，不监听公网）。改编排后重建该容器。
2. 确认网络连通性（见 7.1）：从 wo4 执行 `curl -m 5 http://10.126.126.2:18630/`。
3. 同步插件代码到沙盒宿主的插件目录（保留服务器侧 config.toml，不整文件覆盖）。
4. 在服务器 config.toml 增加 `[upload]` 分区：`enabled = true`；`adapter_api_prefix` 按该 bot 对应的适配器实例完整前缀填写（参考群管同名配置的值）。
5. 重启 maim-bot-core 或经 WebUI 重载插件。
6. 按第 8 节验收标准逐项验证。

## 7. 部署期验证项（两件事必须真机确认）

### 7.1 wo4 → 沙盒宿主 18630 的连通性

从 wo4（10.126.126.3）执行 `curl -m 5 http://10.126.126.2:18630/`。沙盒临时服务未启动时「连接拒绝」属预期（TCP 能到达宿主即可）；超时说明 easytier 路由或端口发布缺失，先检查第 6 节步骤 1 的容器端口映射，再检查 easytier 连通（`ping 10.126.126.2`）。

### 7.2 setsid 后台进程能否躲过 shell_exec 的 hard_timeout

在沙盒 `shell_exec` 中启动 `setsid nohup python3 -m http.server 18630 ... &`，等待超过 hard_timeout 后再 curl 该端口。服务仍存活则编排成立；被连带终止则改用 Jupyter 会话内 `subprocess.Popen(..., start_new_session=True)` 启动（沙盒插件已有 Jupyter 通路，属实现细节切换，不影响方案结构）。

## 8. 验收标准

| # | 场景 | 通过条件 |
|---|------|----------|
| 1 | 小文件（如 5MB）上传 | 群文件可见同名文件；WS 无断连；返回成功文案 |
| 2 | 大文件（如 50MB）上传 | 群文件可见；WS 无断连；上传期间控制链路仅一次 action 调用 |
| 3 | 清理 | 上传完成（含失败）后，沙盒内 `pgrep -f "http.server 18630"` 无结果 |
| 4 | 权限 | 非管理员发起被拒并返回拒绝原因；识别不到发起者拒绝 |
| 5 | 错误暴露 | 文件不存在、napcat retcode 非 0、端口占用时，返回原始错误信息，不静默兜底 |
| 6 | 日志 | 每次上传记录：选路决策（base64/http）、文件大小、目标群号、napcat retcode |

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| napcat 拉取大文件耗时过长，action 调用等待超时（适配器侧超时上限未知） | 真机验证 50MB 档位；napcat 等待时长由宿主 action 调用控制，超时时先缩小文件规模验证链路，再决定是否给上传设大小上限 |
| `http.server` 进程残留（上传中断、插件崩溃） | finally 清理 + 固定端口使残留可发现（残留导致下次探测失败时报错并附清理命令）；pkill 匹配固定端口串，不误杀其他进程 |
| wo4 到沙盒宿主 18630 不可达（easytier 路由/端口发布缺失） | 部署期验证项 7.1 前置；不可达时先修端口发布与内网路由 |
| 大文件 URL 在 easytier 内网明文传输 | 仅内网可达，端口发布绑定内网接口、不暴露公网；符合内网工具不鉴权不公网的既有约定 |
| 双适配器 API 名不唯一 | `adapter_api_prefix` 配置，语义与群管一致；漏配时「API 名称不唯一」错误原文透出，便于定位 |

## 10. 明确不做的事

- 分块/分片上传：协议无 API（约束 #3）。
- 私聊文件上传（`upload_private_file`）：本期仅群文件；私聊场景返回明确提示。
- R2 公网中转：跨机器内网不通时再实现，避免提前引入凭据管理。
- 群管插件改动：`/upload` 已覆盖「人工拿得到 URI」的场景，沙盒链路由沙盒插件自己完成，两插件不互相依赖。
